# Agent 原理与职责

系统中的 Agent 指拥有明确上下文、指令和工具边界的模型角色，不等于独立进程或独立模型服务。文本角色复用 DeepSeek，图片生成由 Seedream 承担。LangGraph 管理研究／文字阶段状态，程序队列管理任务执行。Skills 在 [应用指令目录](../geo_workbench/skills) 中，运行时记录其摘要。

## 1. 入口审核与候选对话

输入是当前上传快照及本次用户要求。入口审核判断矛盾、无依据要求和缺失信息，问题必须能对应用户原话。确定性结构错误由程序先处理，不交给模型猜。

用户处置问题时，入口对话 Agent 可调用 `inspect_product` 读取 JSON 指针、`preview_candidate` 预览修改。候选携带旧值、新值、原话和原因；它不是已经生效的事实。用户确认后，程序检查旧版本并写入新输入／意图版本，再重新审核。

工具循环最多三轮。对话和候选保存在当前任务，不从其他同名商品补资料。入口失败时停留待处理状态，不擅自进入研究。

实现：[intake_dialog.py](../geo_workbench/intake_dialog.py)、[workflow.py](../geo_workbench/workflow.py)。

## 2. 画像选择、采访者与模拟使用者

画像选择依据主题、目标受众、场景和任务，产生最多四个具有不同决策需求的模拟画像。每个画像分配独立会话；最多三份画像访谈同时执行。

每个画像有两轮问答：采访者先探索目标、情境和选择困难；第二轮承接前一轮，并显式加入商品事实讨论取舍。采访者与模拟使用者各自维护消息历史。第一轮不会额外注入完整 FactSet，但任务主题本身可能带有商品线索。

程序逐条保存问答和状态。任一访谈未完成时保留已完成消息，不将部分结果冒充完整研究。模拟使用者不能声称真实购买或实际体验。

实现：[research.audience](../geo_workbench/research.py)。

## 3. 问题地图综合

综合角色读取本次完整模拟访谈与商品事实，整理各画像的决策路径、问题地图、差异、优先级依据和可回答程度。程序检查每个画像是否具有决策路径、问题是否有效；缺失则不继续 Planner。

优先级是模型对当前任务的判断，不是真实市场规模或搜索频率。画像结论可影响选题与表达，不能作为商品性能证据。

## 4. 联网研究

研究角色先生成最多两条查询。程序调用搜索和网页读取工具，进行 URL 规范化、跟踪参数清理、候选域名分散，最多读取三页。网页内容是外部数据，不是系统指令。

证据提取角色从已读取内容中提出摘录。程序要求摘录为读取快照中的真实子串，再分配 evidence ID，并记录来源、范围及匹配状态。高度相似页面标记可能重复，不把多个 URL 当成独立支持。

“成功读取”“摘录可定位”与“语义支持主张”是三个不同判断。品类知识和竞品描述不得提升为本商品事实；失败、空结果和证据不足显式保留。

实现：[research.Tools / evidence](../geo_workbench/research.py)。搜索与读取是该角色的工具，不额外增加搜索 Agent。

## 5. Planner

Planner 接收任务契约、问题地图、模拟访谈摘要、来源和证据包，输出：

- 以读者决策为主线的编辑策略、核心问题与选择依据。
- Blog／详情页各自的大纲、Meta、FAQ 方向、内部链接和结构化数据要求。
- 内部写作 Brief，列出可引用事实／证据、未知项、禁写主张和页级要求。
- 候选品类／竞品比较，标明范围、取舍及证据缺口。

程序检查引用存在性、章节字数预算可行性与结构。规划的字数分配有问题时允许一次修订调用；仍有问题则保留提示，不假装语义已获验证。用户确认当前规划后才能显式启动写作。

实现：[research.plan](../geo_workbench/research.py)、[composition.py](../geo_workbench/composition.py)。

## 6. Writer

Writer 使用已批准版本的商品、规划和证据，生成两页 ContentIR。它调用 `word_count` 提交完整候选，程序检查结构、可见字数和引用是否可解析。模型可读取反馈修订，再显式选择或提交有效候选。

ContentIR 将标题、Meta、章节和 FAQ 与引用分开保存。HTML 由程序渲染，避免模型直接输出任意脚本或结构。字数计算包括可见标题、正文和 FAQ，不将 Meta／JSON-LD 混入读者字数。

Writer 最多四次模型调用，受整个文字尝试的总调用、时间、上下文和 token 预算共同限制。引用通过只说明指针有效，事实支持仍由核验判断。

实现：[content.ModelProvider.agent_call](../geo_workbench/content.py)。

## 7. 事实核验与回归

程序给当前版本的 H1、Meta、章节标题、段落和 FAQ 分配正文单元。核验 Agent 只能按单元 ID 返回判断、来源及理由；不能自行改写“需核对原文”。展示原文由程序从当前版本读取。

核验分清商品事实、外部品类知识、普通背景常识、非事实建议、输入缺失披露。缺失披露必须对应有效的当前输入路径，不能将已有或无法定位的信息说成“未提供”。普通建议不因没有商品证据就自动判错；隐含具体商品属性的建议仍需要支持。

程序检查覆盖、版本、重复／未知 ID、来源范围与必要分类字段。协议或分类错误优先由同一核验角色有限修复，不立刻当成正文错误交 Editor。编辑后使用相同契约做事实回归；未知、冲突和未支持的实际主张保留阻断。

实现：[content.py](../geo_workbench/content.py) 中 `check_bundle`、`bind_checker_results`、`validate_checker_classification`、`validate_ledger` 及回归节点。

## 8. Editor

Editor 读取当前可编辑单元、事实问题和引用，提出 `unit_id / before / after / reason` 操作。需要改变引用时附准确旧／新引用。`word_count` 工具同时预演修改、校验基线和计数字数，不是另一个 Agent。

程序逐项接纳或拒绝操作，返回准确失败位置与可用候选基线。模型不能把旧消息中的候选 ID 当成当前基线；工具选中的候选必须能重建并进入事实回归。

Editor 首次最多四次、返工最多剩余三次，共七次；总预算不足时显式停止，为回归保留调用。最后一轮可提交结构／引用有效但字数未达标的事实修复，最终字数检查仍然生效。

## 9. 图片 Agent

同一 Agent 定义读取已核验正文、商品、风格、主题和目标场景。先在同次低思考调用内构思、自查并修正，再只输出最终 Prompt 字段及 caption/alt；不输出推理、排名或营销效果评分。同调用内自查是指引，程序不能证明它已有效执行。

| 页面 | 内部 Prompt 字段 |
|---|---|
| Blog | visual_concept、product_presence、setting、composition、visual_style、constraints |
| 详情页 | product_identity、variant_arrangement、view_and_framing、background、lighting_and_finish、constraints |

程序把字段串为 Seedream 的文本 `prompt`。比例、背景和 PNG 等另作 API 参数；字段本身不是供应商原生 API。Blog 从全文支持的场景中选择一个有读者关联、能突出商品的创意，避免通用陈列加象征性道具。

Blog 的 `with_user`／`without_user` 各有独立持久会话。前者从商品判断实际使用者／受益者，可为人、犬或其他主体，不固定性别，也不把购买者自动当使用者；无法判断时要求补充。后者不出现人、动物、身体局部或剪影。两者共享来源受限的风格和用户约束，历史与参考图不互读。详情图保持单候选，颜色仅从已确认变体取值，不展开尺码。

自动路径：准备 Prompt → Seedream → 文件／比例／alpha 检查 → DeepSeek 读取实际 PNG → 必要时参考上一版返工。每候选最多三次生成，Blog 合计最多六次。视觉未知不自动重画。

人工路径：原话＋本卡选定原图 → 同一 Agent 映射请求 → 生成一张 → 程序文件检查 → 直接交用户。无后置视觉自检、无自动循环，标记 `not_run_user_edit`，不复制旧版 pass。

原图用于返工；展示图由程序右下角叠加“AI 视觉示意”。新请求关闭供应商可选可见水印；旧资产不覆写。页面选图独立于候选最新版本，只有用户选择／确认才替换已选图。

实现：[images.py](../geo_workbench/images.py)、[图片 Skill](../geo_workbench/skills/images/SKILL.md)。

## 程序承担的职责

导入、来源绑定、批准、任务排序、预算计数、指针解析、版本与旧值校验、渲染、文件有效性、PNG 透明通道、确认与 ZIP 均由程序完成。不要将确定性检查结果解释成模型语义、实物身份或营销效果已被证明。
